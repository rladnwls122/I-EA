## 결정 1 — 자기검증 집계: `ai_generations`가 아니라 **`questions`에 컬럼을 꺼낸다**

### 앞 문서의 "제자리"가 틀렸다

`2026-08-05-dogfooding-four-decisions.md`는 "집계가 필요해지면 `ai_generations`에 판정 요약
컬럼을 얹는 게 제자리"라고 적었다. 같은 문서의 결정 1이 자기검증을 **출제 채팅(SSE)** 으로
옮겨 놓았는데, 그 경로는 `ai_generations` 행을 아예 만들지 않는다
(`authoring-chat.service.ts`는 `prisma.aiGeneration`을 건드리지 않는다).
그 컬럼을 얹었다면 **실사용에서 영원히 비어 있는 컬럼**이 됐을 것이다 —
"꺼져 있으면 데이터가 안 쌓인다"고 지적한 바로 그 순환의 반복이다.

실사용에서 판정이 남는 자리는 하나뿐이다: 저장된 문항의 `metadata.review`.

### Json 안에 있으면 집계가 안 된다 — 이미 한 번 겪었다

부분점수 리포트(`cd273b5`)가 같은 벽을 만났다. rubric 점수가 Json 안에 있어 SQL 집계가
안 됐고, `earned_points`/`rubric_total_points` 두 컬럼을 꺼내 풀었다. 같은 처방을 쓴다.

- `questions.review_verdict` (`VARCHAR(16)`, nullable) — `PASS` | `REVISE` | `ERROR`.
- `metadata.review`는 **그대로 남는다**. 컬럼은 집계용 사본이고, 근거(축·지적 문장)는
  검수 패널이 읽어야 하므로 Json이 정본이다. 둘을 **같은 쓰기 경로에서** 함께 채운다
  (`questions.service`의 create/update 한 곳 — 갈라지면 언젠가 한쪽만 갱신된다).
- 판정이 없던 문항은 `null`이다. `null`과 `ERROR`를 뭉개지 않는다 — "판정 안 함"과
  "판정하려다 실패"는 품질 지표에서 정반대 의미다(결정 B-3의 연장).

### 축 분해는 앱에서 접는다 (전체 비율은 DB 집계)

- 헤드라인(PASS/REVISE/ERROR 비율)은 `groupBy` — **상한 없이 정확해야 하는 숫자**다.
  컬럼을 꺼낸 이유가 그것이다.
- "어느 축이 자주 걸리나"는 축이 Json 안(`metadata.review.axes`)이라 SQL로 못 묶는다.
  축별 서술형 득점률과 **똑같은 선택**을 한다 — 행을 상한(2000) 걸어 받아 앱에서 접는다.
  raw SQL로 조건을 한 벌 더 적으면 언젠가 한쪽만 고쳐진다.
- 회차 축은 **날짜**다(`createdAt` 일자별). 채팅에는 "생성 배치"라는 경계가 없으므로
  배치 단위 집계는 애초에 만들 수 없다. 일자별이면 `npm run quality:generation` 회차와
  대조도 된다.

### 노출 자리

`GET /ai-generations/review-stats` — 자기검증의 도메인 주인이 이 모듈이다.
**본인이 만든 문항만** 집계한다(`creatorId = 요청자`). 남의 품질 수치를 볼 이유가 없고,
ADMIN 전역 집계가 필요해지면 그때 파라미터를 연다.

**뒤집을 경우 비용**: 낮음. 컬럼은 nullable이라 지우면 그만이고, 근거 Json이 정본이라
데이터가 사라지지 않는다. 엔드포인트는 읽기 전용이라 부르는 화면만 접으면 된다.

## 결정 2 — 축별 득점률의 처방: **같은 버튼, 새 필터 하나**

약점 진단 카드는 축마다 "공략 N문항" 버튼이 있고, 서술형 축은 보여 주기만 했다.
막고 있던 건 UI가 아니라 **세션 조립에 "서술형만"을 표현할 수단이 없다**는 것이었다.
`filter.questionTypes`는 객관식/주관식까지만 나눈다 — 주관식 안에서 단답(자동채점)과
서술형(채점기준표)은 같은 값이다.

### 필터 이름은 `rubricOnly`, 판정은 저장 형태로 한다

서술형의 정의를 새로 만들지 않는다. 채점기(`grading.util`)가 이미 쓰는 판정을 그대로 쓴다:
**주관식 + `correctAnswerText` 없음 + `rubric` 있음**. 세 조건을 다 건다 —
`rubric`만 보면 단답 정답이 채워진 뒤 죽은 기준만 남은 문항이 딸려 오고
(`rubricPayload`가 그 조합을 지우지만 과거 데이터가 있다), `correctAnswerText`만 보면
자기채점 2지선다 서술형까지 섞여 득점률 축과 모집단이 어긋난다.

- 이름을 `essayOnly`가 아니라 `rubricOnly`로 둔 이유: 화면 용어("서술형")가 아니라
  **모집단을 정의하는 조건**을 이름에 담아야 득점률 카드와 같은 집합임이 코드에서 읽힌다.
  득점률 축의 모집단도 "채점기준표로 채점된 답안"이다.
- 축(subjectDetailId)과 함께 건다 — 버튼이 달린 줄이 곧 그 축이다.
- 세트가 비면 기존 필터 모드와 같은 실패 메시지다(문항 부족). 새 예외를 만들지 않는다.

**뒤집을 경우 비용**: 낮음. 필터는 선택 필드고 버튼만 숨기면 이전 화면이다.

## 결정 3 — 교체안의 판정: **서버가 metadata를 병합한다** (PATCH 한정)

지금은 캔버스가 **새 문항에만** `metadata: { review }`를 싣는다. 기존 문항에 실으면
metadata가 통째로 교체되면서 우리가 모르는 키(빈칸 번호 `blankIndex`, OX 표시)를 덮어쓰기
때문이다. 그래서 교체안으로 받은 새 판정은 캔버스를 닫으면 사라졌다.

고칠 자리는 **서버**다. 클라이언트가 "다른 키를 지우지 않으려면 먼저 읽어서 합쳐 보내라"를
지키게 만드는 규약은, 지키지 않는 클라이언트가 하나 생기는 순간 조용히 데이터를 지운다.

### 규칙

- `PATCH /questions/:id`의 `metadata`는 **얕은 병합**이다. 보낸 키만 덮어쓰고 나머지는 남는다.
- 키를 **지우는 표현은 값 `null`** 이다(`{ blankIndex: null }`). 필드 자체를 생략하면
  PATCH 규약상 "안 건드림"이라, 병합만 두면 키를 지울 방법이 사라진다 —
  `rubric`의 빈 배열, `tagIds`의 빈 배열과 같은 문법이다.
- 병합 결과가 빈 객체면 컬럼을 `null`로 되돌린다(`stripInternalReview`가 이미 쓰는 규칙과
  같은 이유 — 빈 객체는 화면에서 "메타데이터 있음"으로 읽힌다).
- `POST /questions`(생성)는 병합할 대상이 없으므로 종전대로 그대로 쓴다.
- 병합은 **최상위 한 겹**이다. 깊은 병합은 `review.axes` 같은 배열을 합칠 때 규칙이
  모호해지고(붙이나 갈아치우나), 판정은 통째로 갈아치우는 게 맞다.

프론트는 그 대가로 `metadata: { review }`를 **기존 문항에도** 싣는다.
변경 감지 지문(`questionFingerprint`)에 판정이 들어가므로, 판정이 도착한 카드는
다음 저장에서 실제로 PATCH가 나간다(도착하지 않은 카드는 종전처럼 건너뛴다).

**뒤집을 경우 비용**: 중간. 병합을 되돌리면 기존 문항의 판정이 다시 사라지고,
그 사이 저장된 문항의 `review`는 남는다(데이터 손실은 없다). 클라이언트를 먼저
되돌리지 않고 서버만 되돌리면 **덮어쓰기가 되살아난다** — 순서를 지켜야 한다.
