# 2026-08-05 — 도그푸딩 대기 4건, 결정과 구현

> #33 마지막 코멘트가 "여전히 도그푸딩 선행"으로 남겨 둔 네 항목을 결정하고 구현한다.
> 각 항목에 **왜 지금 결정할 수 있었는지**와 **뒤집을 경우 비용**을 남긴다.

남아 있던 네 항목:

1. 자기검증 기본 켬 여부 — `npm run quality:generation` 수치 몇 회차 후
2. 분류축별 서술형 득점률 — 지금은 전체만. 축당 표본이 하한 3을 거의 못 넘는다
3. `POST /media-assets` 배칭 — 이미지가 많은 문제집에서 왕복의 다수가 될 수 있다
4. 배치 항목의 DTO 형식 검증이 전부-아니면-전무

## 결정 1 — 자기검증: **기본 켬**, 그리고 실사용 경로에 붙인다

### 유예 사유가 실제와 달랐다

"비용이 배가된다"가 유예 근거였는데, 배가되는 건 **호출 수**(배치당 1회 추가)이지
토큰이 아니다. 판정 응답은 문항당 한두 줄 JSON이고 입력은 방금 만든 문항 본문뿐이라,
문항을 다시 만드는 생성 호출과는 크기가 다르다.

더 큰 문제는 순환이었다: **꺼져 있으면 "품질이 미달인지"를 볼 데이터가 안 쌓인다.**
도그푸딩으로 판단하겠다고 미뤄 둔 항목이, 도그푸딩 데이터를 만들지 않는 설정에 묶여 있었다.

### 그런데 켜는 것만으로는 아무 일도 일어나지 않았다

자기검증은 비동기 생성 파이프라인(`POST /ai-generations`)에만 붙어 있었고,
**화면은 그 경로를 부르지 않는다** — 캔버스는 SSE 출제 채팅을 쓴다(`web/lib/api.ts` 주석에도
"지금 이 두 함수를 부르는 화면은 없다"고 적혀 있다). 환경변수만 뒤집었다면 실사용에서는
달라지는 게 하나도 없었을 것이다.

그래서 검증을 **사람이 문항을 다듬는 자리**에 붙였다:

- 출제 채팅이 문항 블록을 낸 턴이면, 본문 스트림이 끝난 뒤 판정을 돌려 `event: review` 프레임으로 흘린다.
- 카드는 **먼저** 뜨고 배지가 나중에 채워진다. 판정을 기다렸다 같이 주면 사람이 기다리는 시간만 는다.
- 판정 실패는 채팅 오류가 **아니다** — 조용히 배지가 안 뜬다. 멀쩡히 생성된 문항이 실패로 보이면 안 된다.
- 판정은 제안 카드(적용 전) → 캔버스 카드(적용 후) → 저장(`metadata.review`) → 문항 상세 검수 패널로 이어진다.
  고칠 마음이 있는 시점은 문항 상세를 열 때가 아니라 **적용할지 정하는 그 순간**이다.

### UX 판단으로 남길 것

- **PASS를 강조하지 않는다.** 통과가 기본값이라 강조하면 화면이 초록 배지로 뒤덮이고 REVISE가 묻힌다.
- **세 상태를 뭉개지 않는다.** 기다리는 중(스피너) / 판정 없음(아무것도 안 그림) / 판정됨. 뭉개면
  배지가 영원히 스피너로 남거나, 판정 못 한 문항이 통과처럼 보인다.
- **크레딧을 더 받지 않는다.** 이 호출은 사용자가 요청한 게 아니라 우리가 품질을 위해 거는 것이다.
- **끄는 값만 열거한다**(`false`/`0`/`off`/`no`). 오타 하나로 품질 장치가 조용히 꺼지는 쪽보다,
  끄려는 의도를 명시하게 하는 쪽이 낫다.
- 판정이 늦게 도착하는 사이 사용자가 다음 질문을 보낼 수 있다 — 그래서 판정은 **그 턴의 자리**를
  기억했다가 붙인다(ref를 쓰면 엉뚱한 메시지에 붙는다).

### 서버가 문항 블록을 다시 읽는다

판정 index가 카드와 맞으려면 서버·프런트 파서가 **같은 배열**을 만들어야 한다.
그래서 `authoring-chat.review.ts`가 프런트 규칙(펜스 스캔·관대한 JSON 정화·유형 정규화)을
그대로 옮겨 왔고, 같은 입력에 같은 결과가 나오는지 스펙으로 고정했다.
⚠️ 프런트 파서를 고치면 여기도 같은 커밋에서 고쳐야 한다 — 어긋나면 **조용히 틀린 배지**가 뜬다.

**뒤집을 경우 비용**: `AI_SELF_REVIEW=false` 한 줄. 코드 경로는 그대로 남고 배지만 안 뜬다.

## 결정 2 — 분류축별 서술형 득점률: **낸다. 단, 표본 미달 축을 숨기지 않는다**

"축당 표본이 하한 3을 거의 못 넘는다"는 관찰은 맞다. 하지만 그건 **지표를 내지 말아야 할 이유가
아니라 표본 미달을 어떻게 보여줄지의 문제**다. 약점 진단(#37)이 이미 같은 문제를 `needsMoreData`로
풀어 뒀다 — 판정은 미루되 "이 유형은 표본이 N개라 아직 판정 안 한다"고 말해 준다.
숨기기만 하면 학습자는 자기가 푼 서술형이 어디로 갔는지 알 수 없다.

### 구현 판단

- 축은 하위요소(subjectDetail) — `bySubjectDetail`·약점 진단과 같은 축이라 화면 사이에서 말이 통한다.
- **왜 raw SQL이 아닌가**: 축은 questions 쪽 컬럼이라 Prisma groupBy로 못 묶는다. 남는 선택지는
  (a) 축마다 쿼리, (b) raw SQL, (c) 행을 받아 앱에서 접기. (b)는 1차 응시·범위 필터 조건을
  **SQL로 한 벌 더** 적어야 해서 언젠가 한쪽만 고쳐진다. (c)를 골랐다 — 대상이 "채점기준표로
  채점된 서술형 답안"뿐이라 모집단이 작고, 집계와 **같은 where 객체**를 그대로 재사용한다.
- 헤드라인(전체 득점률)은 그대로 DB 집계다. 상한 밖에서 정확해야 하는 숫자이고, 컬럼을 꺼낸 이유가
  그것이었다. 축별 조회에만 상한(2000)이 붙는다.
- 정렬은 **낮은 득점률부터**. 화면 첫 줄이 곧 다음에 손볼 곳이어야 한다. 같은 비율이면 표본이 많은 쪽.
- 전체가 하한 미달이면 축별 조회를 **아예 하지 않는다** — 부분집합이라 볼 것도 없다.
- 축이 하나뿐이면 화면에서 분해를 접는다(전체와 같은 숫자를 두 번 그리는 셈이다).

**뒤집을 경우 비용**: 응답 필드(`rubricScore.byDetail`)는 선택 필드라 화면만 접으면 된다.

## 결정 3 — `POST /media-assets` 배칭: **한다**

문항 저장이 배치가 된 뒤(20문항 첫 저장 65회 → 6회), 남은 왕복의 다수가 실제로 이미지 등록이 됐다.
그림 20장이면 `POST /media-assets`가 20번 나간다 — 문항 60회를 1회로 줄여 놓고 이미지에 20회를 쓰는 모양이다.

- `POST /media-assets/batch` — 상한 100(문항 50보다 크다: 이미지는 문항 하나에 여러 장이 붙고,
  항목 하나가 URL·크기 몇 개뿐이라 페이로드가 작다).
- 결과는 문항 배치와 같은 **항목별**. 하나가 실패해도 나머지는 등록되고, 실패한 것만
  기준선에서 빠져 다음 저장에서 다시 시도된다.
- **등록을 멱등으로 만들었다**(단건도 같이): 같은 사람이 같은 URL을 같은 대상에 다시 등록하면
  새 행을 만들지 않고 기존 행을 돌려준다. 중복 행은 "이 문항의 미디어 목록"에 같은 이미지가
  여러 번 뜨는 것으로 나타나고, 저장이 중간에 실패해 재시도할 때 실제로 생긴다.
- 대상 존재 확인은 **앞에서 한 번에** 한다(항목마다 같은 문항을 다시 조회하면 배치가 DB N+1이 된다 —
  HTTP 왕복을 줄이려고 만든 자리에서 앞뒤가 안 맞는다).
- 지문 이미지와 문항 이미지를 **같은 배치**에 싣는다. 따로 보내면 왕복이 다시 둘로 갈린다.

**뒤집을 경우 비용**: 단건 엔드포인트가 그대로 살아 있어 어댑터 한 줄만 되돌리면 된다.

## 결정 4 — 배치 항목의 DTO 검증: **항목별로 격리한다**

서비스 계층 실패는 항목별로 격리해 놓고 **형식 검증만 전부-아니면-전무**였다. 20문항 중 한 문항의
difficulty가 6이면 나머지 19문항까지 400 하나로 되돌아왔다 — 배치가 없애기로 한 바로 그 실패 모드다
("문항 하나 때문에 나머지를 되돌리는 건 저장이 아니라 사고", `batch-result.ts`).

- 배치 DTO는 `items`에 `@ValidateNested`를 걸지 않는다. 배열 자체·상한만 파이프가 본다
  (그건 항목이 아니라 요청의 형태다).
- 항목은 서비스가 `validateBatchItems(items, 단건DTO)`로 하나씩 검증한다. **같은 DTO 클래스,
  같은 옵션**(`common/validation-options.ts`를 전역 파이프와 나눠 갖는다) — 배치가 검증을
  우회하는 샛길이 되면 단건 PATCH로는 못 넣는 값이 배치로는 들어간다.
- 실패 사유는 필드 경로까지 짚는다(`choices.0.content`) — 배치 응답은 "몇 번째 카드가 왜"를
  화면에 옮기는 자리라 필드를 못 짚으면 고칠 데를 찾지 못한다.
- 담기 배치에서 **형식이 깨진 항목은 자리(displayOrder)를 차지하지 않는다**. 담기지 않은 문항 몫으로
  번호를 비워 두면 순서에 구멍이 생기고, 뒤이은 순서 저장이 그 구멍을 메우며 화면과 어긋난다.
- 응답은 요청 순서로 정렬해 돌려준다(클라이언트는 index로 되짚지만, 사람이 읽을 때 자리가 섞여 있으면 대조가 어렵다).

**뒤집을 경우 비용**: DTO에 `@ValidateNested`를 되돌리면 예전 동작이다(권장하지 않는다).

## 남은 것

- **자기검증 수치의 누적** — 이제 실사용에서 판정이 돌지만, "REVISE 비율이 회차마다 어떻게
  변하는가"를 모으는 자리는 아직 없다(문항별 `metadata.review`에 기록만 된다).
  집계가 필요해지면 `ai_generations`에 판정 요약 컬럼을 얹는 게 제자리다.
- **축별 득점률의 처방 연결** — 약점 진단은 축마다 "공략 N문항" 버튼이 있는데, 서술형 축은
  아직 보여 주기만 한다. 서술형만 모은 세트를 만들 수단(문항 유형 필터)이 세션 조립에 없다.
- **교체안의 판정** — 기존 문항을 교체하는 제안은 캔버스에서 배지로 보이지만 저장되지 않는다
  (metadata는 통째로 교체되는 필드라 다른 키를 덮어쓸 수 있다). 병합이 필요하면 서버가 할 일이다.
